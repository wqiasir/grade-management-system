  1. `flask init-db --force` → 走 Alembic 迁移建表，`flask db current` 显示 `fba8e95c58f8 (head)`；
     库中 7 张表 = 6 张业务表 + `alembic_version`。
  2. `flask seed` → 新增用户 3、学生 1、教师 1、课程 1；重复执行不产生重复数据。
  3. `flask run` → 访问 <http://127.0.0.1:5000/> 返回 `HTTP 200`，页面显示"**系统已启动**"，

  4. 库中口令均为 `scrypt` 哈希（如 `scrypt:32768:8:1$...`），无明文。
- **测试结果**：`pytest` 通过 **12** 条 / 失败 **0** 条；
  `--cov=gradeapp` 覆盖率 **97%**（198 语句 / 漏 2，22 分支 / 部分 5）；
  分模块：`models.py` 100%、`extensions.py` 100%、`__init__.py` 95%。
- **遇到的问题**：
  1. **虚拟环境没有 pip**：`python -m venv` 建出的 `.venv` 只有 `python.exe`，没有 `pip` 与 `activate`
     脚本，`ensurepip` 与 `pip install` 均报 `PermissionError: [Errno 13]`（写不进 Python 自己创建的临时目录）。
  2. **迁移脚本弃用警告**：`flask db init` 生成的 `migrations/env.py` 调用 `db.get_engine()`，
     在 Flask-SQLAlchemy 3.1 下触发 `DeprecationWarning`（该接口将在 3.2 移除）。
  3. **Windows 下临时库删除失败风险**：测试夹具在 teardown 直接删 SQLite 文件时，
     连接池仍持有句柄会导致删除失败。
- **如何解决**：
  1. 在放宽文件权限的终端中删除 `.venv` 后重新创建并安装依赖，装到
     Flask 3.1.3 / Flask-SQLAlchemy 3.1.1 / Flask-Migrate 4.1.0 / Flask-WTF 1.3.0 / SQLAlchemy 2.0.54
     / pytest 8.4.2；随后 `pip freeze > requirements.txt` 冻结。运行测试/迁移时把 `TMP`/`TEMP`
     指向仓库内可写目录，规避沙箱对临时目录的限制。
  2. 把 `env.py` 的 `get_engine()` 改为优先使用 `db.engine`（保留旧版本分支），警告消除，测试输出干净。
  3. 夹具 teardown 顺序改为 `db.session.remove()` → `db.drop_all()` → `db.engine.dispose()` → 删文件，
     并对 `OSError` 容错。
- **遗留问题**：
  - 首页 `index.html` 目前是独立模板，R2 引入 `base.html` 后应重构为模板继承。
  - `exam_type` 未加数据库 CHECK 约束（有意保留灵活性，便于 R10 Excel 导入扩展考核类型）。
  - 学生/课程删除的级联策略只在数据库层做了 `ondelete="CASCADE"`，
    业务层规则（如"有成绩的学生能否删除"）留到 R4 / R5 决定。
  - 覆盖率虽已达 97%，但 R11 要求的是**权限矩阵与边界**覆盖，不能替代。
- **下轮计划**：R2 — 用户认证。`auth.py` 蓝图、`login.html`、`base.html` 骨架、
  `werkzeug.security` 口令校验、种子账号登录演示、`tests/test_auth.py`。

- **测试结果**：`pytest` 通过 **103** 条 / 失败 **0** 条（R1 12 + R2 35 + R3 56）；

  `decorators.py` 97%、`admin.py` 91%、`score.py` 94%、`dashboard.py` 90%、`__init__.py` 96%。
- **遇到的问题**：
  1. **SQLAlchemy 2.0 的 `case()` 不接受 `type_=`**：报表里想用 `func.sum(case(..., type_=Integer))`
     统计及格条数，直接 `TypeError: case() got an unexpected keyword argument 'type_'`，统计页整片 500。
  2. **"最后一个管理员"这条规则在 HTTP 路径上不可达**：发请求的管理员自己一定是可用管理员，
     所以"要停用的对象是最后一个可用管理员"在正常操作下永远不会成立 —— 最初写的 HTTP 版测试断言不出来。
  3. **测试里切换角色时旧会话没清掉**：R2 的设计是"已登录再访问登录页直接回首页"，
     所以测试里连续 `login()` 两个账号时，第二次请求被 302 挡回首页，页面还是**第一个账号**的。
  4. **真实服务上 CSRF token 每次渲染都变**：冒烟脚本里复用早先取到的 token，POST 被拦成 400
     （而 pytest 里 `WTF_CSRF_ENABLED=False`，完全掩盖了这个问题）。
  5. **菜单的"占位项"分支绕过了端点检查**：`endpoint_exists()` 明明写好了，但 `menu_for_user` 里
     优先判断 `pending is None`，于是"既写了 `endpoint` 又标了 `pending`"的项直接 `url_for()` 抛 `BuildError`。
     顺带发现原来的 `except Exception` 太宽 —— 这种真实缺陷会被它悄悄吞掉。
- **如何解决**：
  1. 汇总查询改成"一次取 `count` + `avg`，另一次用子查询 `where(score >= 60)` 取及格条数"，
     分组查询里也去掉 `type_=`（改用 Python 侧 `int()` 归一）。SQLite 的 `SUM(CASE …)` 返回整数，口径不变。
  2. 这条规则改在**模型层**单测 `User.deactivation_blocker()`：覆盖"只剩一个可用管理员 → 被挡"
     与"还有别的可用管理员 → 放行"两种状态，并在测试注释里写明它是防"运维在库层面停用其他管理员"的兜底；
     另补一条 HTTP 版的正常停用测试，保证路由本身可用。
  3. 测试里切换角色前先 `POST /auth/logout`，并在注释里写明"已登录状态下再登录不会换人"。
  4. 冒烟脚本区分两个取 token 的时机：登录态从**首页**取（`current_token`），
     未登录从登录页取（`fresh_token`），且**紧邻 POST 前**再取一次；顺带把"缺 token 的 POST → 400"
     单列为一条断言，正好证明 CSRF 在鉴权之前生效。
